# Capability Contract — design spec (v1 draft)

This document defines the **Capability Contract** between **cloud-labs**
(`optics-digital-twin`) and **`lab_automation`**. It is the Phase 0 artifact for
the larger Universal Component refactor. Subsequent implementation PRs (Phases
1–9 in the roadmap) reference this file.

**Status:** v1 draft. Edits require discussion; numbered open questions at the
end of the file track unresolved points.

---

## 1. Purpose

We want:

1. **Decoupled repos.** Cloud-labs and `lab_automation` are separately versioned
   public repos. Neither imports the other at runtime for schema information.
2. **Magical UI.** The frontend renders rich, interactive widgets per tunable
   (3D-looking pose handles, sliders with units, motor nudge buttons, …) — not
   a generic list of text boxes.
3. **Hardware safety.** Both layers validate commands against the same schema,
   so a stray `exposure_time` sent to a mirror is rejected at both the UI gate
   and the hardware gate.
4. **A single source of truth.** Component capabilities are declared **once**,
   in JSON, and read by both repos.

The Capability Contract is the data shape that makes all four possible.

### Non-goals

- This document does **not** redefine `tunables` / `measurables` — those are
  already in `backend/lab_model/domain/component.py` and `backend/lab_model/README.md`.
- It does **not** define new primitives. It only describes how each component
  declares **which** primitives it supports.
- It does **not** specify the TELEOP transport (REST vs WebSocket) — see
  Phase 8 in the roadmap.

## 2. Three-layer architecture

```text
┌────────────────────────────────────────────────────────────────────┐
│                  component_catalog.json                            │  ← THE LAW
│  (per lab-view bundle; the only schema declaration that exists)    │
└────────────────────┬───────────────────────────┬───────────────────┘
                     │                           │
              (read at boot)               (read at boot)
                     │                           │
                     ▼                           ▼
        ┌────────────────────────┐   ┌──────────────────────────┐
        │   cloud-labs           │   │   lab_automation         │
        │                        │   │                          │
        │ • Widget Registry      │   │ • Maps catalog entries   │
        │   (closed v1 set)      │   │   to OpticalComponent    │
        │ • Renders UI from      │   │   subclasses + SDK calls │
        │   capabilities         │   │ • Validates inputs at    │
        │ • Dispatches primitives│   │   the hardware boundary  │
        │   declared by catalog  │   │                          │
        └────────────────────────┘   └──────────────────────────┘
```

**Rules:**

- Both repos **read** the catalog. Neither **writes** it.
- Cloud-labs **does not import `lab_automation`** for schema purposes. It can
  still import `lab_automation` for hardware dispatch (current behavior); that
  is unchanged.
- `lab_automation` **does not import `cloud-labs`**. It receives the catalog
  as a constructor argument: `OpticalExperiment(catalog=<dict>, ...)`.
- The catalog is **human-editable JSON**. It can also be generated by a
  helper script (`scripts/regenerate_catalog_from_lab_automation.py`) that
  introspects `lab_automation` Python classes — but at runtime, both repos
  read only the file.

## 3. JSON shape

The catalog is a single JSON object. Today, `component_library.json` is a
top-level **array**; under this spec it becomes an **object** with two keys:
`schema_version` and `components`. The existing per-component fields are
preserved; a new `capabilities` block is added.

### 3.1. Skeleton

```json
{
  "schema_version": 1,
  "components": {
    "tag_18": {
      "id": "mirror_curved",
      "type": "OPTICAL_MIRROR",
      "name": "Curved Mirror (OC)",
      "tag_id": "tag_18",
      "size": { "width": 62, "height": 62 },
      "height_mm": 60,
      "properties": { /* unchanged: physical specs */ },
      "motor_ids": [1, 3],
      "motor_controller": "wifi_stepper1",
      "capabilities": {
        "statecontrol": {
          "tunables": { /* see §3.2 */ },
          "measurables": { /* see §3.3 */ }
        },
        "telemetry": {
          "teleop": { /* see §3.4 */ },
          "live_feed": { /* see §3.4 */ }
        },
        "primitives": [ /* see §3.5 */ ]
      }
    }
  }
}
```

### 3.2. `capabilities.statecontrol.tunables`

Maps a tunable field name → widget descriptor (read-only in the UI; writes go through primitives).

```json
"statecontrol": {
  "tunables": {
    "nominal_pose":             { "widget": "TablePose" },
    "nominal_motor_positions":  { "widget": "JsonInspector" },
    "exposure_time_ms":         { "widget": "FloatRange", "min": 10, "max": 1000, "default": 200, "unit": "ms" }
  }
}
```

Legacy catalogs may still use flat `capabilities.tunables`; the loader normalizes via `normalize_capabilities()`.

### 3.3. `capabilities.statecontrol.measurables`

Maps a measurable field name → widget descriptor. These are *receipts*; the UI renders them read-only under **STATE CONTROL → Measurables**. Fresh values come from **`RECORD_MEASURABLES`**.

```json
"statecontrol": {
  "measurables": {
    "last_optimization_score": { "widget": "NumberBadge", "format": ".3f" },
    "motor_rotations":         { "widget": "MotorRotationsReadout" },
    "camera_image":            { "widget": "ImageViewer", "format": "png" }
  }
}
```

### 3.4. `capabilities.telemetry`

Declares **live session** metadata and stream endpoints. Runtime state lives in `components[tag].telemetry` (not in measurables). The UI shows session JSON read-only under **TELEMETRY**; start/stop/jog use **PRIMITIVES**.

**TeleOp** (per-component lease):

```json
"telemetry": {
  "teleop": {
    "pose": {
      "widget": "TeleopJog",
      "step_mm": [0.5, 2.0, 10.0],
      "step_deg": [0.5, 2.0, 10.0]
    }
  },
  "live_feed": {
    "stream": {
      "widget": "MJPEGViewer",
      "url": "/api/components/{tag_id}/telemetry/stream"
    }
  }
}
```

Runtime teleop slice: `{ "active", "ready", "lease_ts", "last_jog_ts", "last_error" }`. Jog is allowed only when `active && ready`.

**Live feed** uses a **`stream`** channel only (legacy `preview` / `JPEGPoll` removed). `{tag_id}` in URLs is substituted per instance at render time.

### 3.5. `capabilities.primitives`

A list of primitive IDs the component supports. **This list is the single
source for what dispatch will allow.** It replaces ad-hoc flags like `is_movable`.

```json
"primitives": [
  "MOVE_COMPONENT",
  "SET_EXPOSURE",
  "STORE_COMPONENT",
  "PLACE_FROM_STORAGE",
  "PICK_COMPONENT",
  "HOVER",
  "PLACE_FROM_HOVER",
  "RECORD_MEASURABLES",
  "START_TELEOP",
  "END_TELEOP",
  "TELEOP_JOG",
  "START_LIVE_FEED",
  "END_LIVE_FEED"
]
```

Recommended UI display order (enforced in `frontend/js/primitives/index.js`):

1. `MOVE_COMPONENT` + tunable writers (`SET_EXPOSURE`, `SET_MOTOR_SETPOINT`, …)
2. Manipulation (`STORE_COMPONENT`, pick/hover/place, …)
3. Workflow (`RECORD_MEASURABLES`, `OPTIMIZE`, …)
4. Telemetry sessions (TeleOp + live feed) — always last

Primitive ids must be drawn from `backend/lab_model/primitives/ids.py::PrimitiveId`.
Unknown ids are a hard-fail at boot (see §5).

**Static (non-movable) components** are expressed by **omitting** movement
primitives from this list — e.g. a ceiling camera bolted to the rig declares
only `["RECORD_MEASURABLES"]`. Dispatch refuses `MOVE_COMPONENT` for it
naturally; no `is_movable` flag needed.

## 4. Widget vocabulary (v1)

The **closed set** of widget types cloud-labs ships with. Adding a widget is a
cloud-labs PR (one React/JS component + one entry in the registry).

### 4.1. Tunable widgets

| Widget                | Underlying data shape                    | Notes |
|-----------------------|------------------------------------------|-------|
| `TablePose`           | `{ x, y, rotation }` (mm, mm, deg)       | Canvas-draggable + numeric inputs. Renders the component icon on the layout. |
| `NudgeMotorGroup`     | `{ "<motor_id>": float, ... }` (deg)     | +/- buttons per motor; reads `motor_ids`, `step_deg`. |
| `FloatRange`          | `float`                                  | Slider + numeric input. Reads `min`, `max`, `default`, `unit`. |
| `IntRange`            | `int`                                    | Same, step 1. |
| `Boolean`             | `bool`                                   | Toggle switch. |
| `StringDropdown`      | `string`                                 | Reads `options: string[]`. |
| `StorageSlot`         | `{ i, j }`                               | Q3 storage grid picker. |

### 4.2. Measurable widgets

| Widget                  | Underlying data shape                    | Notes |
|-------------------------|------------------------------------------|-------|
| `PoseReadout`           | `{ x, y, rotation }` (or extended)       | Read-only; shown when measurables carry encoder confirmation. |
| `MotorRotationsReadout` | `{ "<motor_id>": float, ... }`           | Read-only dial group. |
| `ImageViewer`           | `{ path, format, source, cam_id, ... }`  | Loads PNG/JPEG via the camera-image route. |
| `NumberBadge`           | `float \| int \| null`                   | Reads `format` (printf-style). |
| `Timestamp`             | `string` (ISO-8601)                      | Relative time display (“3 s ago”). |

### 4.3. Telemetry widgets

| Widget                    | Endpoint kind             | Notes |
|---------------------------|---------------------------|-------|
| `MJPEGViewer`             | HTTP multipart MJPEG      | Mounted as `<img src=…>`. |
| `JPEGPoll`                | HTTP single JPEG          | Polled by the frontend at `default_fps`. Lower-latency than MJPEG. |
| `LiveCoordinatesReadout`  | WebSocket JSON frames     | Renders a live x/y/z/rot readout during TELEOP. |

### 4.4. Universal fallback

| Widget          | Behavior |
|-----------------|----------|
| `JsonInspector` | Read-only formatted JSON view. Used by the soft-fallback path (see §5). Not normally declared in the catalog; cloud-labs picks it automatically when the catalog references a widget the running build doesn’t know. |

### 4.5. Vocabulary stability

The v1 vocabulary is **frozen at first release**. New widgets bump
`schema_version` if they are declared **required** for any built-in component.
Adding a widget that exists only for new optional capabilities does **not**
bump the version (existing catalogs keep working).

## 5. Versioning & validation policy

Hybrid: hard-fail on required-field mismatch; soft-fall back on optional
widgets.

### 5.1. Hard failures (cloud-labs refuses to boot)

- Catalog `schema_version` is not in cloud-labs’s `SUPPORTED_SCHEMA_VERSIONS`.
- A component entry is missing a required field (`id`, `type`, `tag_id`,
  `capabilities.primitives`).
- A primitive id in `capabilities.primitives` is not in
  `lab_model.primitives.PrimitiveId`.
- A widget descriptor’s required config is missing (e.g. `FloatRange` without
  `min` and `max`).

### 5.2. Soft fallbacks (cloud-labs boots, logs warning)

- A widget name in the catalog is unknown to the running build → renders the
  field with `JsonInspector` (read-only), logs a single warning at boot.
- A measurable / telemetry channel listed in the catalog is missing from
  current state → renders an empty placeholder (the field is declared but
  has no data yet).

### 5.3. Validation locations

| Where             | What is validated                                              |
|-------------------|----------------------------------------------------------------|
| **Boot (cloud-labs)** | Schema version + structural integrity (§5.1).               |
| **Boot (lab_automation)** | Each catalog entry maps to a known `OpticalComponent` subclass; per-component capability fields are recognized hardware-side. |
| **Per request (cloud-labs)** | Dispatch refuses a primitive not declared in the target component’s `capabilities.primitives`. |
| **Per request (lab_automation)** | Tunable updates outside the catalog’s declared range / set are rejected at the hardware boundary. |

Both repos must reject the same inputs for the same reasons. The catalog is
the only schema either repo references.

## 6. `lab_automation` integration contract

### 6.1. Constructor signature

```python
class OpticalExperiment:
    def __init__(
        self,
        mock: bool = False,
        catalog: Optional[Dict[str, Any]] = None,  # new
        ...
    ):
        ...
```

- `catalog=None` → preserves current behavior (hardcoded steppers / cameras /
  IPs) so existing `lab_automation` users outside cloud-labs are not broken.
- `catalog=<dict>` → opt-in capability-driven mode: drivers are configured
  from the catalog, validation uses the catalog.

### 6.2. What `lab_automation` reads from the catalog

Only the **hardware-relevant** fields:

- `type` (drives which `OpticalComponent` subclass to instantiate).
- `tag_id`, `motor_ids`, `motor_controller` (per-component hardware wiring).
- `capabilities.tunables[*]` — uses `min`, `max`, `options`, `default` for
  input validation. Ignores `widget`.
- `capabilities.primitives` — gates which methods on the resulting Python
  object are exposed to dispatch.

### 6.3. What `lab_automation` ignores

- `capabilities.tunables[*].widget` (cloud-labs concern).
- `capabilities.measurables[*].widget` (cloud-labs concern).
- `capabilities.telemetry[*].url` (cloud-labs serves the routes).
- `properties.*` (these are display-only physical specs).

## 7. Migration from today

### 7.1. Current shape (top-level array)

```json
[
  {
    "id": "mirror_curved",
    "type": "OPTICAL_MIRROR",
    "name": "Curved Mirror (OC)",
    "tag_id": "tag_18",
    "size": { "width": 62, "height": 62 },
    "height_mm": 60,
    "properties": { "radius_of_curvature": "100mm", "reflectivity": 0.98 },
    "motor_ids": [1, 3],
    "motor_controller": "wifi_stepper1"
  }
]
```

### 7.2. After (object with `schema_version` + `components`)

```json
{
  "schema_version": 1,
  "components": {
    "tag_18": {
      "id": "mirror_curved",
      "type": "OPTICAL_MIRROR",
      "name": "Curved Mirror (OC)",
      "tag_id": "tag_18",
      "size": { "width": 62, "height": 62 },
      "height_mm": 60,
      "properties": { "radius_of_curvature": "100mm", "reflectivity": 0.98 },
      "motor_ids": [1, 3],
      "motor_controller": "wifi_stepper1",
      "capabilities": {
        "tunables": {
          "nominal_pose":            { "widget": "TablePose" },
          "nominal_motor_positions": { "widget": "NudgeMotorGroup", "motor_ids": [1, 3], "step_deg": 2.5 }
        },
        "measurables": {
          "last_optimization_score": { "widget": "NumberBadge", "format": ".3f" },
          "motor_rotations":         { "widget": "MotorRotationsReadout" }
        },
        "telemetry": {},
        "primitives": [
          "MOVE_COMPONENT", "MOVE_MOTOR", "MOTOR_SEND_HOME", "MOTOR_SET_ZERO",
          "OPTIMIZE", "STORE_COMPONENT", "PLACE_FROM_STORAGE",
          "PICK_COMPONENT", "HOVER", "PLACE_FROM_HOVER", "SCAN_ROTATE_IN_PLACE",
          "RECORD_MEASURABLES"
        ]
      }
    }
  }
}
```

### 7.3. Migration script

`scripts/archive/migrate_component_library_to_capabilities.py` (one-shot):

- Reads the current array form.
- Wraps it in `{ schema_version: 1, components: { ... } }`.
- For each component, infers a `capabilities` block from the existing `type`
  + `motor_ids` using a small lookup table (mirror/lens/camera/etc. presets).
- Writes the result back, preserving formatting.

Per-component customizations are hand-edited afterward.

## 8. Implementation checklist (forward references)

This is **not** the implementation plan; it’s a forward index so PR descriptions
can link here.

| Phase | Touches this contract by …                                              |
|-------|--------------------------------------------------------------------------|
| 1     | Canvas reads `tunables.nominal_pose`; no widget registry yet.            |
| 2     | `OBSERVE_MEASURABLES` → `RECORD_MEASURABLES`; updates `primitives` lists. |

| 5     | Catalog format migration (§7); `lab_automation` opt-in `catalog=` arg.   |

| 8     | TELEOP-specific tunables (`teleop_active`) declared per-component.       |
| 9     | Global `/api/video-feed/*` sunset; only per-component endpoints remain.  |

## 9. Open questions

These are unresolved in v1; revisit before the affected phase ships.

1. **`OPTIMIZE` strategy declaration.** Today `OPTIMIZE` takes a strategy name
   (`NEWTON`, `COBYLA`) and per-strategy params. Should the catalog declare
   which strategies a component supports (e.g.
   `"capabilities.optimize.strategies": ["NEWTON", "COBYLA"]`)? Probably yes,
   but the shape isn’t finalized.
2. **Composite widgets.** Some UIs are most natural as one composite (e.g. a
   storage tunable that is `{ slot: {i,j}, presence: "storage" }` shown as a
   single grid picker). Do we allow composite widgets that read multiple
   tunable fields? Or do we keep one widget per field and let layout group
   them? Lean: one widget per field for v1; revisit.
3. **Per-bench widget overrides.** Two benches with the same component type
   might want different widget config (different `step_deg` on the nudge
   buttons, say). Per-bundle catalog already supports this; just confirm via
   a worked example.
4. **TELEOP-specific capability block.** Phase 8 will likely need a fourth
   capability bucket (`teleop`) declaring which channels are jog-driven and
   their widget. Defer specification to Phase 8.
5. **Schema-version negotiation.** If we later need to support multiple
   schema versions in one cloud-labs build, what does the negotiation look
   like? For v1 the answer is “only one version supported at a time, hard
   fail otherwise”; revisit if we ever ship breaking changes mid-version.
